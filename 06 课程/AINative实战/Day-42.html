AI Native 实战课程 - Day 42: 第十二章 - 性能优化

📖 今日导读

你的 AI Native 产品上线了，用户蜂拥而至——然后你发现：API 账单飙升到每月数万美元，P99 延迟超过 10 秒，GPU 利用率却只有 30%。这是 2025-2026 年几乎所有 AI Native 产品在规模化阶段遇到的共同噩梦。LLM 的强大能力背后是巨大的计算成本和延迟开销，不解决性能问题，再好的产品设计也无法落地。

今天我们将系统学习 AI Native 产品的三大性能优化维度：Token 优化与成本控制（让每一分钱花在刀刃上）、延迟优化（让用户感知到"快"）、模型级联（用小模型处理简单任务，大模型只处理复杂任务）。这些技术不是锦上添花，而是 AI Native 产品从原型走向生产的生命线。

🔍 核心概念

1. Token 优化与成本控制

Token 优化 是 AI Native 产品成本控制的第一战场。LLM 按 Token 计费，一个典型的 RAG 系统每次请求消耗 2000-8000 tokens，日活 10 万用户意味着每天数千万 Token 的消耗。

① Prompt 压缩

Prompt 是最大的 Token 消耗源。优化策略包括：

  • 系统提示精简：将冗长的 System Prompt 从 2000 tokens 压缩到 500 tokens，保留核心指令，移除"礼貌用语"和冗余示例
  • 上下文窗口管理：采用滑动窗口 + 摘要策略，当对话超过阈值时，将早期对话压缩为摘要，而非保留全部历史
  • RAG 上下文精选：不是检索越多越好——5 条高相关文档片段远胜于 20 条低质量片段

② Prompt 缓存

2025 年，主流 LLM 提供商（OpenAI、Anthropic、Google）都支持了 Prompt Caching：相同前缀的请求可以复用 KV Cache，减少 50-90% 的重复计算。关键实践：

  • 将 System Prompt 和工具定义放在请求最前面（可缓存部分）
  • 保持前缀的稳定性，避免每次请求都微调措辞
  • OpenAI 的自动缓存对超过 1024 tokens 的前缀自动生效

③ 结构化输出优化

使用 JSON Schema 约束输出格式，而非通过 Prompt 描述"请用 JSON 格式返回"。这不仅减少输出 Token（约节省 20-30%），还消除了格式错误导致的重试成本。OpenAI 的 Structured Outputs 和 Anthropic 的 Tool Use 都原生支持这一能力。

2. 延迟优化：流式输出、量化、批处理

延迟优化 直接决定用户体验。研究表明，AI 产品的响应延迟超过 3 秒，用户满意度下降 40%。延迟由两部分组成：

  • 首 Token 延迟（TTFT）：从请求发出到第一个 Token 返回，受模型大小和 Prompt 长度影响
  • Token 生成速度（TPS）：每秒生成的 Token 数，受 GPU 带宽和解码策略影响

① 流式输出（Streaming）

流式输出不减少总延迟，但大幅改善感知延迟。用户看到文字逐字出现，心理等待时间缩短 60-70%。2025-2026 年的最佳实践：

  • 所有面向用户的 LLM 调用都应使用流式输出
  • 前端用 SSE（Server-Sent Events）或 WebSocket 接收
  • 流式状态下显示"思考中"或逐步渲染 Markdown

② 量化（Quantization）

模型量化 是用精度换速度的核心技术。将模型权重从 FP16 降到 INT8 或 INT4，显存占用减少 2-4 倍，推理速度提升 1.5-3 倍，精度损失通常在 1-3% 以内。

量化方式 显存节省 速度提升 精度影响 适用场景
FP16 → INT8 50% 1.5x <1% 生产默认选择
FP16 → INT4 75% 2-3x 1-3% 对延迟敏感的场景
FP8（H100/H200） 50% 2x <0.5% 新一代 GPU 专用

③ 投机解码（Speculative Decoding）

这是 2025-2026 年最热门的推理加速技术。核心思路：用一个小模型（Draft Model）快速生成候选 Token 序列，再用大模型并行验证。如果小模型猜对了（通常命中率 70-85%），就跳过逐 Token 解码，实现 2-3 倍加速。

代表项目： - EAGLE-2：特征级投机解码，动态树搜索，3x 加速 - Medusa：多头解码，不需要额外 Draft 模型 - MLPSpeculator：轻量 MLP Draft 模型，已集成到 vLLM

④ 连续批处理（Continuous Batching）

传统批处理等所有请求完成才释放资源。连续批处理动态插入新请求、移除已完成请求，GPU 利用率从 30% 提升到 90%+。vLLM 的 PagedAttention 和 SGLang 的 RadixAttention 是最佳实现。

3. 模型级联：简单任务用小模型

模型级联（Model Cascading / Model Routing）是成本优化的杀手锏。核心洞察：80% 的用户请求是简单任务，不需要最强的模型。

架构模式：

用户请求 → 路由器（Router）→ 复杂度评估
  ├── 简单任务（80%）→ 小模型（GPT-4o-mini / Claude Haiku / Qwen-7B）
  ├── 中等任务（15%）→ 中模型（GPT-4o / Claude Sonnet）
  └── 复杂任务（5%） → 大模型（GPT-4.5 / Claude Opus / DeepSeek-R1）

路由器设计：

  1. 基于规则的路由器：按任务类型（闲聊→小模型，代码生成→大模型）硬编码路由规则，简单但不够灵活
  2. 基于 ML 的路由器：训练轻量分类器（BERT 或小型 LLM），根据输入特征预测最优模型。RouteLLM 项目显示，这种方式可以实现 2 倍成本节省且质量损失 <1%
  3. 级联式路由器：先用小模型生成回答，评估置信度，置信度不够再升级到大模型。Anthropic 的企业客户报告这种方式实现了 40-70% 的成本降低

关键指标： - 路由准确率（Router Accuracy）：路由器选对模型的比例，目标 >95% - 成本节省率（Cost Saving）：相比全用大模型的节省比例 - 质量损失（Quality Degradation）：路由后回答质量的下降幅度，目标 <2%

import hashlib
import json
import time
from dataclasses import dataclass, field
from typing import Optional
from collections import defaultdict

# ==================== 第一部分：Token 成本追踪器 ====================

@dataclass
class TokenUsage:
    """Token 使用量记录"""
    prompt_tokens: int = 0
    completion_tokens: int = 0
    cached_tokens: int = 0
    model: str = ""
    latency_ms: float = 0.0

@dataclass
class CostTracker:
    """
    Token 成本追踪器
    记录每次请求的 Token 使用量和成本，生成分析报告
    """
    # 模型定价（$/1M tokens）
    pricing: dict = field(default_factory=lambda: {
        "gpt-4o": {"input": 2.50, "output": 10.00, "cached_input": 1.25},
        "gpt-4o-mini": {"input": 0.15, "output": 0.60, "cached_input": 0.075},
        "claude-sonnet-4-20250514": {"input": 3.00, "output": 15.00, "cached_input": 0.30},
        "claude-haiku": {"input": 0.25, "output": 1.25, "cached_input": 0.03},
    })

    records: list = field(default_factory=list)

    def record(self, usage: TokenUsage) -> dict:
        """记录一次请求并计算成本"""
        price = self.pricing.get(usage.model, {"input": 1.0, "output": 3.0, "cached_input": 0.5})

        # 缓存命中的 Token 用折扣价
        fresh_input = usage.prompt_tokens - usage.cached_tokens
        input_cost = (fresh_input * price["input"] + usage.cached_tokens * price["cached_input"]) / 1_000_000
        output_cost = usage.completion_tokens * price["output"] / 1_000_000

        record = {
            "model": usage.model,
            "prompt_tokens": usage.prompt_tokens,
            "completion_tokens": usage.completion_tokens,
            "cached_tokens": usage.cached_tokens,
            "cache_hit_rate": usage.cached_tokens / max(usage.prompt_tokens, 1),
            "input_cost": input_cost,
            "output_cost": output_cost,
            "total_cost": input_cost + output_cost,
            "latency_ms": usage.latency_ms,
            "timestamp": time.time(),
        }
        self.records.append(record)
        return record

    def report(self) -> dict:
        """生成成本分析报告"""
        if not self.records:
            return {"error": "No records yet"}

        total_cost = sum(r["total_cost"] for r in self.records)
        total_cached = sum(r["cached_tokens"] for r in self.records)
        total_prompt = sum(r["prompt_tokens"] for r in self.records)
        avg_latency = sum(r["latency_ms"] for r in self.records) / len(self.records)

        # 按模型统计
        model_stats = defaultdict(lambda: {"count": 0, "cost": 0, "tokens": 0})
        for r in self.records:
            model_stats[r["model"]]["count"] += 1
            model_stats[r["model"]]["cost"] += r["total_cost"]
            model_stats[r["model"]]["tokens"] += r["prompt_tokens"] + r["completion_tokens"]

        return {
            "total_requests": len(self.records),
            "total_cost_usd": round(total_cost, 4),
            "avg_cost_per_request": round(total_cost / len(self.records), 6),
            "overall_cache_hit_rate": round(total_cached / max(total_prompt, 1), 3),
            "avg_latency_ms": round(avg_latency, 1),
            "model_breakdown": dict(model_stats),
        }


# ==================== 第二部分：语义缓存 ====================

class SemanticCache:
    """
    基于精确匹配的 LLM 响应缓存
    生产环境应替换为向量数据库（如 Redis + embedding）实现语义相似度匹配
    """

    def __init__(self, ttl_seconds: int = 3600):
        self.cache: dict[str, dict] = {}
        self.ttl = ttl_seconds
        self.hits = 0
        self.misses = 0

    def _make_key(self, messages: list[dict], model: str) -> str:
        """生成缓存键：对 messages 的内容做 hash"""
        content = json.dumps(messages, sort_keys=True, ensure_ascii=False) + model
        return hashlib.sha256(content.encode()).hexdigest()[:16]

    def get(self, messages: list[dict], model: str) -> Optional[dict]:
        """查询缓存"""
        key = self._make_key(messages, model)
        if key in self.cache:
            entry = self.cache[key]
            if time.time() - entry["timestamp"] < self.ttl:
                self.hits += 1
                return entry["response"]
            else:
                del self.cache[key]
        self.misses += 1
        return None

    def set(self, messages: list[dict], model: str, response: dict):
        """写入缓存"""
        key = self._make_key(messages, model)
        self.cache[key] = {"response": response, "timestamp": time.time()}

    def stats(self) -> dict:
        total = self.hits + self.misses
        return {
            "hits": self.hits,
            "misses": self.misses,
            "hit_rate": round(self.hits / max(total, 1), 3),
            "cache_size": len(self.cache),
        }


# ==================== 第三部分：模型级联路由器 ====================

# 任务复杂度枚举
SIMPLE = "simple"      # 闲聊、格式化、简单问答
MEDIUM = "medium"      # 总结、翻译、代码补全
COMPLEX = "complex"    # 多步推理、长文分析、复杂代码

class ModelRouter:
    """
    模型级联路由器
    根据任务复杂度选择最优模型，在成本和质量之间取得平衡
    """

    def __init__(self, cost_tracker: Optional[CostTracker] = None):
        # 模型层级定义
        self.model_tiers = {
            SIMPLE: "gpt-4o-mini",       # $0.15/M tokens
            MEDIUM: "gpt-4o",            # $2.50/M tokens
            COMPLEX: "gpt-4o",           # 复杂任务用最强模型
        }

        # 复杂度评估的关键词规则（生产环境应使用 ML 分类器）
        self.complexity_rules = {
            SIMPLE: [
                "你好", "谢谢", "是什么", "怎么用", "帮我翻译",
                "格式化", "总结一下", "hello", "hi", "what is"
            ],
            COMPLEX: [
                "分析", "对比", "方案", "架构", "优化", "debug",
                "重构", "策略", "推理", "证明", "设计一个",
                "implement", "analyze", "refactor", "design"
            ],
        }

        self.cost_tracker = cost_tracker or CostTracker()
        self.routing_stats = defaultdict(int)

    def classify_complexity(self, user_message: str) -> str:
        """
        评估任务复杂度
        生产环境建议：使用轻量分类器（如微调的 BERT）替代规则匹配
        """
        msg = user_message.lower()

        # 规则一：短消息通常是简单任务
        if len(user_message) < 20:
            return SIMPLE

        # 规则二：检查复杂度关键词
        for keyword in self.complexity_rules.get(COMPLEX, []):
            if keyword in msg:
                return COMPLEX

        # 规则三：包含代码块通常是中等以上任务
        if "```" in user_message or "def " in user_message:
            return COMPLEX

        # 规则四：长消息通常是更复杂的任务
        if len(user_message) > 500:
            return MEDIUM

        return SIMPLE

    def route(self, user_message: str) -> dict:
        """路由请求到最优模型"""
        complexity = self.classify_complexity(user_message)
        model = self.model_tiers[complexity]
        self.routing_stats[complexity] += 1

        return {
            "model": model,
            "complexity": complexity,
            "reason": f"消息长度 {len(user_message)} 字符，"
                     f"复杂度评估为 {complexity}，"
                     f"路由到 {model}"
        }

    def get_stats(self) -> dict:
        """获取路由统计"""
        total = sum(self.routing_stats.values())
        return {
            "total_routed": total,
            "distribution": {
                k: {"count": v, "percentage": round(v / max(total, 1) * 100, 1)}
                for k, v in self.routing_stats.items()
            },
            "estimated_savings": self._estimate_savings()
        }

    def _estimate_savings(self) -> dict:
        """估算相比全用大模型的成本节省"""
        # 假设每请求平均 1000 prompt tokens + 500 completion tokens
        avg_prompt = 1000
        avg_completion = 500

        # 全用大模型的成本
        full_cost = (avg_prompt * 2.50 + avg_completion * 10.00) / 1_000_000

        # 路由后的加权成本
        weighted_cost = 0
        for complexity, count in self.routing_stats.items():
            model = self.model_tiers[complexity]
            price = self.cost_tracker.pricing.get(model, {"input": 1.0, "output": 3.0})
            cost_per = (avg_prompt * price["input"] + avg_completion * price["output"]) / 1_000_000
            weighted_cost += cost_per * count

        total = sum(self.routing_stats.values()) or 1
        avg_weighted = weighted_cost / total

        return {
            "full_model_cost_per_request": round(full_cost, 6),
            "routed_cost_per_request": round(avg_weighted, 6),
            "savings_percentage": round((1 - avg_weighted / max(full_cost, 0.000001)) * 100, 1)
        }

class OptimizedLLMClient:
    """
    集成了性能优化的 LLM 客户端
    包含：模型路由 + 语义缓存 + 成本追踪

    def __init__(self):

        self.cost_tracker = CostTracker()

    def chat(self, messages: list[dict], force_model: Optional[str] = None) -> dict:
        """
        优化后的聊天接口

        流程：
        1. 检查语义缓存
        2. 路由到最优模型
        3. 调用 LLM（此处模拟）
        4. 写入缓存
        5. 记录成本
        """
        user_msg = next((m["content"] for m in reversed(messages) if m["role"] == "user"), "")

        # Step 1: 查缓存
        cached = self.cache.get(messages, force_model or "auto")
        if cached:
            cached["from_cache"] = True
            return cached

        # Step 2: 路由
        routing = self.router.route(user_msg)
        model = force_model or routing["model"]

        # Step 3: 调用 LLM（生产环境替换为真实 API 调用）
        start = time.time()
        # response = openai_client.chat.completions.create(model=model, messages=messages, stream=True)
        response = {  # 模拟响应
            "content": f"[模拟] 使用 {model} 处理了您的请求: {user_msg[:50]}...",
            "model": model,
        }
        latency = (time.time() - start) * 1000

        # Step 4: 写缓存
        self.cache.set(messages, model, response)

        # Step 5: 记录成本（模拟数据）
        usage = TokenUsage(
            prompt_tokens=len(user_msg) // 3,  # 粗略估算
            completion_tokens=len(response["content"]) // 3,
            cached_tokens=0,
            model=model,
            latency_ms=latency,
        )
        cost_record = self.cost_tracker.record(usage)

        response["from_cache"] = False
        response["routing"] = routing
        response["cost"] = cost_record
        return response

    def dashboard(self) -> dict:
        """生成性能仪表盘"""
        return {
            "cost_report": self.cost_tracker.report(),
            "cache_stats": self.cache.stats(),
            "routing_stats": self.router.get_stats(),
        }

✅ 最佳实践

成本优化黄金法则

  1. 80/20 原则：80% 的请求可以用小模型处理。通过模型级联路由，企业客户通常能实现 40-60% 的成本节省，质量损失 <2%。不要"一刀切"用最强模型。

  2. 缓存一切可缓存的：Prompt Caching 是最低成本的优化——只需调整 Prompt 的排列顺序（不变内容在前，变化内容在后），就能获得 30-50% 的成本折扣。语义缓存则能进一步对相似查询复用结果。

  3. Token 预算意识：给每个功能模块设定 Token 预算。比如"客服摘要"功能限制 500 tokens 输入 + 200 tokens 输出，超出则截断或降级。没有预算控制的 AI 功能是成本黑洞。

延迟优化清单

  1. 必须流式输出：所有面向用户的 LLM 调用都应使用 Streaming。流式不减少总延迟，但感知延迟降低 60-70%。这是性价比最高的用户体验优化。

  2. 预计算与预热：将 RAG 检索、Embedding 计算等前置步骤异步化。用户输入时就开始检索，LLM 调用时直接用结果，减少端到端延迟 30-50%。

  3. 量化作为默认选项：自部署模型时，INT8 量化应该是默认配置而非可选优化。精度损失 <1%，但速度提升 1.5 倍、显存节省 50%。

架构设计原则

  1. 可观测性优先：从第一天就集成 Token 统计、延迟追踪、成本归因。没有度量就没有优化。推荐在 LLM 调用层统一埋点，记录每次请求的模型、Token 数、延迟、成本、缓存命中状态。

  2. 渐进式优化：先用最简单的优化（Prompt Caching + 流式输出），再做模型级联，最后考虑自部署和量化。过早优化是万恶之源——先让产品跑起来，用数据驱动优化决策。

🤔 思考题

  1. 成本-质量权衡：你的 AI Native 产品中，哪些功能对质量敏感（必须用最强模型），哪些对延迟敏感（必须快速响应），哪些对成本敏感（可以接受稍慢或稍差）？请尝试设计一个模型路由策略。

  2. 缓存的边界：语义缓存可以大幅提升性能，但也可能导致用户看到"过期"的回答。在你的业务场景中，缓存 TTL 应该设为多久？哪些数据绝对不能缓存？

  3. 自建 vs 用 API：当你的 LLM 月度 API 支出超过 $10,000 时，是否应该考虑自建推理服务？请从成本、运维复杂度、灵活性三个维度分析自建（vLLM/TensorRT-LLM）vs 使用 API（OpenAI/Anthropic）的优劣。
