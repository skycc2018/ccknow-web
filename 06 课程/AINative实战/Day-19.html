🎓 AI Native 实战课程 - Day 19: 第四章 - 上下文即状态

在传统软件里，状态住在数据库里；在 AI Native 产品里，状态住在上下文窗口里。你往上下文里放了什么，就决定了 AI 能做什么——上下文就是系统的全部"记忆"和"工作台"。

📖 今日导读

Day-18 我们学了「Prompt 即接口」——把用户的一句话变成一次可靠的 API 调用。但接口只解决了"怎么调"的问题，还有一个更根本的问题：AI 凭什么做出正确的判断？

答案是：上下文。

LLM 没有数据库，没有持久状态，它能看到的全部信息就是上下文窗口里的那些 token。窗口里有什么，它就知道什么；窗口里缺什么，它就会"幻觉"。这意味着：上下文的质量 = 产品的质量。

2025 年，Shopify CEO Tobi Lütke 提出了「上下文工程（Context Engineering）」这个概念，取代了流行的「Prompt Engineering」。这个转变的实质是：我们不再只关注"怎么写一句好指令"，而是要管理整个上下文窗口的信息架构——什么该放进去、什么该拿走、什么该压缩、什么该缓存。

今天这一课，我们从架构视角重新理解上下文：它不是"传给模型的一段文字"，而是 AI Native 产品的核心状态管理系统。

🔍 核心概念

1. 为什么说"上下文即状态"？

在传统 Web 应用里，状态管理是这样工作的：

用户操作 → 后端处理 → 写入数据库 → 下次请求时从数据库读取

状态是持久的、结构化的、可查询的。数据库就是"真相来源"。

在 AI Native 应用里，模型没有持久记忆。它的工作方式是：

上下文窗口 [系统提示 + 工具定义 + 历史对话 + 检索知识 + 用户输入] → 模型推理 → 输出

模型能看到、能"记住"、能据此推理的全部信息，就是上下文窗口里的内容。窗口之外的世界，对模型来说不存在。

这就是「上下文即状态」的核心含义：上下文窗口就是 AI 的全部"工作内存"。你管理上下文的方式，就等于你管理应用状态的方式。

2. 上下文窗口的五层信息架构

一个精心设计的上下文窗口，应该像操作系统的内存管理一样分层：

┌─────────────────────────────────────────────┐
│  第一层：身份层（Identity）                      │
│  系统提示 + 角色定义 + 行为规则                    │
│  特征：常驻不变，占 15-20%                       │
├─────────────────────────────────────────────┤
│  第二层：能力层（Capabilities）                   │
│  工具定义 + 函数签名 + Schema                    │
│  特征：按需加载，占 10-15%                       │
├─────────────────────────────────────────────┤
│  第三层：知识层（Knowledge）                      │
│  RAG 检索结果 + 文档片段 + 外部数据               │
│  特征：动态组装，占 30-40%                       │
├─────────────────────────────────────────────┤
│  第四层：历史层（History）                        │
│  对话记录 + 工具调用结果 + 中间推理               │
│  特征：可压缩，占 20-30%                        │
├─────────────────────────────────────────────┤
│  第五层：即时层（Immediate）                      │
│  当前用户输入 + 最新工具结果                      │
│  特征：优先级最高，占 10-15%                     │
└─────────────────────────────────────────────┘

每一层都有不同的生命周期、更新频率和优先级。上下文工程的本质，就是在这有限的窗口空间里做信息的取舍和编排。

3. "Lost in the Middle"：上下文不是越多越好

2024 年斯坦福和加州大学的研究（Liu et al.）发现了一个关键现象：LLM 对上下文中间位置的信息关注度显著下降。

位置 模型注意力 信息回忆准确率
开头（系统提示附近） 最高 ~85-90%
中间 最低 ~55-70%
末尾（用户输入附近） 高 ~80-85%

这意味着：即使你把所有相关信息都塞进上下文，如果关键信息落在"中间盲区"，模型照样可能忽略它。

实践启示： - 最重要的指令和约束放在系统提示（开头） - 最新的、与当前任务最相关的放在靠近用户输入的位置（末尾） - 中间放相对稳定、不直接影响当前决策的背景信息

4. 上下文的成本经济学

上下文窗口不只是技术问题，更是成本问题。以 2025-2026 年主流模型为例：

模型 上下文窗口 输入价格（每 1M token） 200K token 单次成本
GPT-4o 128K $2.50 ~$0.32
Claude 3.5 Sonnet 200K $3.00 ~$0.60
Gemini 2.5 Pro 1M $1.25 ~$0.25
DeepSeek-V3 128K $0.27 ~$0.035

如果一个 AI Agent 每天处理 1000 次对话，每次对话平均使用 50K token 上下文，一个月下来：

  • GPT-4o: ~$375/月
  • Claude: ~$450/月
  • DeepSeek: ~$52/月

上下文优化直接影响运营成本。通过缓存、压缩、按需检索等技术，可以减少 50-90% 的输入 token，这是 AI Native 产品商业可行性的关键。

5. 从 Prompt Engineering 到 Context Engineering

这个概念转变反映了 AI 产品工程的成熟：

维度 Prompt Engineering Context Engineering
关注点 单条指令的措辞 整个上下文窗口的信息架构
方法 手工调优模板 动态组装 + 自动检索 + 压缩
粒度 任务级 系统级
状态 无状态 有状态（上下文本身就是状态）
可测试性 靠感觉 靠 Eval Suite + 结构化评分
角色 写提示词的人 设计信息流架构的工程师

正如 《AI Native：从概念到落地》 第四章所强调的：上下文不是"传给模型的一段话"，而是整个系统的状态总线。

💼 最新案例

案例一：Cursor——代码库即上下文

Cursor（2024-2026 年最火的 AI 编辑器）是「上下文即状态」理念的最佳实践者。

核心创新：Cursor 没有把整个代码库塞进上下文（那会消耗数百万 token），而是建立了一套智能上下文组装系统：

  1. 代码索引：用嵌入向量索引整个代码库的每个函数、类、文件
  2. 相关性检索：当用户提问时，根据当前文件、光标位置、最近编辑的文件，自动检索最相关的代码片段
  3. 上下文分层：系统提示（编辑器规则）→ 项目配置（.cursorrules）→ 相关代码 → 当前文件 → 用户输入
  4. 动态裁剪：根据对话进展，动态替换上下文中的代码片段

结果：用户在百万行代码库中工作时，Cursor 的上下文窗口里永远只放最相关的 50-100K token，但体验上仿佛 AI "理解"整个项目。

数据：Cursor 在 2025 年估值达到 90 亿美元，日活用户超过百万。它的成功证明：上下文管理能力是 AI 编程工具的核心竞争力。

案例二：Letta（原 MemGPT）——让 AI 自己管理上下文

Letta 是一个更激进的案例：它让 LLM 自己决定上下文里应该放什么。

灵感来源：操作系统的虚拟内存管理。当物理内存（上下文窗口）不够时，操作系统会把不常用的数据换出到磁盘（外部存储），需要时再换入。

Letta 的做法： - 给 LLM 两个特殊工具：core_memory_append 和 core_memory_replace - LLM 可以自主决定：哪些信息值得保留在有限的上下文窗口里，哪些应该存到外部 - 当对话变长，LLM 自己压缩旧对话，把关键事实提取到"核心记忆"中 - 核心记忆始终在上下文窗口里，保证长期一致性

效果：在长期对话场景中，Letta 的记忆一致性比传统滑动窗口方案高出 40% 以上。用户在第 50 轮对话中提到的偏好，在第 200 轮对话中仍然被准确引用。

启示：最优雅的上下文管理不是人类设计的固定规则，而是赋予 AI 自主管理上下文的能力——这正是 AI Native 的核心理念：让 AI 成为系统的一等公民。

案例三：Anthropic Claude Code——CLAUDE.md 作为持久上下文

Anthropic 的 Claude Code（2025）引入了一个简单但强大的模式：CLAUDE.md 文件。

在每个项目根目录放一个 CLAUDE.md 文件，Claude Code 启动时自动读取它作为持久上下文。内容包括： - 项目架构概述 - 编码规范 - 常用命令 - 已知问题和注意事项

这个模式的精妙之处在于： - 版本控制友好：CLAUDE.md 和代码一起提交，团队共享 - 渐进式积累：每次对话中发现的新知识可以追加到文件中 - 零额外基础设施：不需要向量数据库，不需要记忆服务，就是个 Markdown 文件

到 2026 年，这个模式已经被广泛采纳：OpenAI Codex 用 AGENTS.md，Cursor 用 .cursorrules，Windsurf 用 .windsurfrules——本质上都是持久化上下文配置。

项目：构建一个分层上下文管理器

下面我们用 Python 实现一个生产级的上下文管理器，它能自动管理上下文的分层、压缩和预算分配。

"""
上下文管理器 —— AI Native 应用的状态管理核心
演示如何将上下文窗口当作操作系统的内存来管理
"""

import json
import time
from dataclasses import dataclass, field
from typing import Literal
from enum import Enum


class ContextLayer(Enum):
    """上下文分层定义"""
    IDENTITY = "identity"       # 第一层：身份（系统提示）
    CAPABILITIES = "capabilities"  # 第二层：能力（工具定义）
    KNOWLEDGE = "knowledge"     # 第三层：知识（RAG 检索）
    HISTORY = "history"         # 第四层：历史（对话记录）
    IMMEDIATE = "immediate"     # 第五层：即时（当前输入）


@dataclass
class ContextItem:
    """上下文条目"""
    content: str
    layer: ContextLayer
    token_count: int
    priority: float = 1.0          # 优先级 0-1，越高越不容易被淘汰
    created_at: float = field(default_factory=time.time)
    last_accessed: float = field(default_factory=time.time)
    access_count: int = 0
    metadata: dict = field(default_factory=dict)

    def touch(self):
        """记录访问，用于 LRU 策略"""
        self.last_accessed = time.time()
        self.access_count += 1


@dataclass
class LayerBudget:
    """每层的 token 预算"""
    layer: ContextLayer
    max_tokens: int
    min_tokens: int = 0
    current_tokens: int = 0

    @property
    def remaining(self) -> int:
        return self.max_tokens - self.current_tokens

    @property
    def utilization(self) -> float:
        return self.current_tokens / self.max_tokens if self.max_tokens > 0 else 0


class ContextManager:
    """
    分层上下文管理器

    核心思想：上下文窗口 = 操作系统的物理内存
    - 分层管理，每层有独立的 token 预算
    - LRU + 优先级的淘汰策略
    - 自动压缩历史对话
    - 动态组装最终上下文
    """

    def __init__(self, total_token_budget: int = 128000):
        self.total_budget = total_token_budget
        self.items: list[ContextItem] = []

        # 默认预算分配（可根据场景调整）
        self.budgets = {
            ContextLayer.IDENTITY: LayerBudget(
                ContextLayer.IDENTITY,
                max_tokens=int(total_token_budget * 0.15)  # 15%
            ),
            ContextLayer.CAPABILITIES: LayerBudget(
                ContextLayer.CAPABILITIES,
                max_tokens=int(total_token_budget * 0.10)  # 10%
            ),
            ContextLayer.KNOWLEDGE: LayerBudget(
                ContextLayer.KNOWLEDGE,
                max_tokens=int(total_token_budget * 0.35)  # 35%
            ),
            ContextLayer.HISTORY: LayerBudget(
                ContextLayer.HISTORY,
                max_tokens=int(total_token_budget * 0.25)  # 25%
            ),
            ContextLayer.IMMEDIATE: LayerBudget(
                ContextLayer.IMMEDIATE,
                max_tokens=int(total_token_budget * 0.15)  # 15%
            ),
        }

        # 用于压缩历史的摘要存储
        self._history_summaries: list[str] = []

    def add(self, content: str, layer: ContextLayer,
            priority: float = 1.0, metadata: dict = None) -> ContextItem:
        """添加一个上下文条目"""
        # 粗略估算 token 数（实际项目中用 tiktoken）
        token_count = len(content) // 2  # 简化估算：约 2 字符 = 1 token

        budget = self.budgets[layer]

        # 如果当前层超预算，触发淘汰
        while budget.current_tokens + token_count > budget.max_tokens:
            evicted = self._evict_from_layer(layer)
            if not evicted:
                print(f"⚠️ 层 {layer.value} 空间不足，无法添加新条目")
                break

        item = ContextItem(
            content=content,
            layer=layer,
            token_count=token_count,
            priority=priority,
            metadata=metadata or {}
        )

        self.items.append(item)
        budget.current_tokens += token_count

        # 身份层和能力层不淘汰，但检查是否超限
        if layer in (ContextLayer.IDENTITY, ContextLayer.CAPABILITIES):
            if budget.current_tokens > budget.max_tokens:
                print(f"⚠️ {layer.value} 超出预算！考虑精简系统提示或工具定义")

        return item

    def _evict_from_layer(self, layer: ContextLayer) -> bool:
        """
        从指定层淘汰最低优先级 + 最久未访问的条目
        类似操作系统的页面置换算法
        """
        layer_items = [
            item for item in self.items
            if item.layer == layer
            and item.layer not in (ContextLayer.IDENTITY, ContextLayer.CAPABILITIES)
        ]

        if not layer_items:
            return False

        # 综合评分：优先级 × 0.6 + 最近访问时间 × 0.4
        now = time.time()
        layer_items.sort(key=lambda x: (
            x.priority * 0.6 + 
            (1 - (now - x.last_accessed) / 3600) * 0.4  # 1小时内的访问算活跃
        ))

        # 淘汰评分最低的
        victim = layer_items[0]
        self.items.remove(victim)
        self.budgets[layer].current_tokens -= victim.token_count

        # 如果是历史层，记录摘要后再淘汰
        if layer == ContextLayer.HISTORY:
            summary = self._compress_item(victim)
            if summary:
                self._history_summaries.append(summary)

        return True

    def _compress_item(self, item: ContextItem) -> str:
        """
        压缩一个历史条目为简短摘要
        实际项目中应调用 LLM 生成摘要
        这里用简单的截断模拟
        """
        content = item.content
        if len(content) > 100:
            return f"[摘要] {content[:80]}..."
        return content

    def assemble_context(self, user_input: str) -> list[dict]:
        """
        组装最终发送给 LLM 的上下文

        按层级顺序组装，确保：
        1. 身份层在最前面（高注意力）
        2. 知识层在中间
        3. 即时层在最后（高注意力）

        遵循 "Lost in the Middle" 原则
        """
        messages = []

        # 第一层：身份（系统提示）
        identity_items = [i for i in self.items if i.layer == ContextLayer.IDENTITY]
        if identity_items:
            system_content = "\n\n".join(i.content for i in identity_items)
            messages.append({"role": "system", "content": system_content})

        # 第二层：能力（工具定义在实际 API 调用中通过 tools 参数传入）
        # 这里用系统消息补充说明
        cap_items = [i for i in self.items if i.layer == ContextLayer.CAPABILITIES]
        if cap_items:
            cap_content = "\n\n".join(i.content for i in cap_items)
            messages.append({
                "role": "system", 
                "content": f"可用工具说明：\n{cap_content}"
            })

        # 第三层：知识（RAG 检索结果）
        knowledge_items = sorted(
            [i for i in self.items if i.layer == ContextLayer.KNOWLEDGE],
            key=lambda x: x.priority,
            reverse=True
        )
        if knowledge_items:
            knowledge_content = "\n---\n".join(i.content for i in knowledge_items)
            messages.append({
                "role": "system",
                "content": f"相关知识参考：\n{knowledge_content}"
            })

        # 历史摘要（如果有被压缩的历史）
        if self._history_summaries:
            summary_text = "\n".join(self._history_summaries[-5:])  # 只保留最近5条摘要
            messages.append({
                "role": "system",
                "content": f"之前的对话摘要：\n{summary_text}"
            })

        # 第四层：历史对话
        history_items = [i for i in self.items if i.layer == ContextLayer.HISTORY]
        for item in history_items:
            item.touch()  # 记录访问
            messages.append(json.loads(item.content))  # 假设存储的是 JSON 格式的消息

        # 第五层：即时输入（放在最后，获得高注意力）
        user_input_tokens = len(user_input) // 2
        imm_budget = self.budgets[ContextLayer.IMMEDIATE]

        # 清除旧的即时层内容
        self.items = [i for i in self.items if i.layer != ContextLayer.IMMEDIATE]
        imm_budget.current_tokens = 0

        # 添加新的用户输入
        self.add(user_input, ContextLayer.IMMEDIATE, priority=1.0)
        messages.append({"role": "user", "content": user_input})

        return messages

    def get_stats(self) -> dict:
        """获取上下文使用统计"""
        total_used = sum(b.current_tokens for b in self.budgets.values())
        stats = {
            "total_budget": self.total_budget,
            "total_used": total_used,
            "utilization": f"{total_used / self.total_budget * 100:.1f}%",
            "layers": {}
        }
        for layer, budget in self.budgets.items():
            layer_items = [i for i in self.items if i.layer == layer]
            stats["layers"][layer.value] = {
                "budget": budget.max_tokens,
                "used": budget.current_tokens,
                "utilization": f"{budget.utilization * 100:.1f}%",
                "item_count": len(layer_items)
            }
        return stats

        layer=ContextLayer.CAPABILITIES,

    )

    ctx.add(
        content="2025年全国餐饮收入5.2万亿，同比增长5.3%。火锅品类闭店率28%，茶饮品类闭店率35%。",
        layer=ContextLayer.KNOWLEDGE,
        priority=0.9,
        metadata={"source": "中国餐饮年报2025"}
    )
    ctx.add(
        content="北京朝阳区奶茶店密度全国最高，每万人拥有4.2家奶茶店，饱和度已达警戒线。",
        layer=ContextLayer.KNOWLEDGE,
        priority=0.8,
        metadata={"source": "美团研究院2025"}
    )

    # 4. 模拟对话历史
    ctx.add(
        content=json.dumps({"role": "user", "content": "我想在朝阳区开一家奶茶店，可行吗？"}),
        layer=ContextLayer.HISTORY,
        priority=0.5
    )
    ctx.add(
        content=json.dumps({"role": "assistant", "content": "根据数据，朝阳区奶茶市场高度饱和..."}),
        layer=ContextLayer.HISTORY,
        priority=0.5
    )

    # 5. 组装最终上下文
    messages = ctx.assemble_context("那如果改开咖啡店呢？有没有数据支持？")

    # 打印统计信息
    stats = ctx.get_stats()
    print("=" * 50)
    print("📊 上下文使用统计")
    print("=" * 50)
    print(f"总预算: {stats['total_budget']:,} tokens")
    print(f"已使用: {stats['total_used']:,} tokens ({stats['utilization']})")
    print()
    for layer_name, layer_stats in stats["layers"].items():
        bar = "█" * int(float(layer_stats["utilization"].strip('%')) / 5)

              f"{layer_stats['used']:>6,} / {layer_stats['budget']:>6,} tokens "
              f"({layer_stats['utilization']}, {layer_stats['item_count']} 条)")
    print()

    # 打印组装后的消息结构
    print("📨 发送给 LLM 的消息结构:")
    for i, msg in enumerate(messages):
        role = msg["role"]
        content_preview = msg["content"][:60].replace("\n", " ")
        print(f"  [{i}] {role}: {content_preview}...")

    return messages

✅ 最佳实践

基于 2025-2026 年行业领先者的实践，以下是上下文工程的核心最佳实践：

1. 预算先行，不要"塞满再说"

在设计 AI 功能的第一天就确定上下文预算分配。参考比例：身份 15%、能力 10%、知识 35%、历史 25%、即时 15%。具体比例根据场景调整——客服场景可能需要更多历史，RAG 场景需要更多知识。

2. 善用缓存，降低重复成本

Anthropic、OpenAI、Google 都提供服务端 Prompt 缓存。系统提示和工具定义几乎不变，应该缓存它们。Anthropic 的 Prompt Caching 可以将缓存部分的成本降低 90%。一个每月 $500 的 API 账单，通过缓存优化可以降到 $100 以下。

3. 压缩历史，保留关键

不要无限制地保留完整对话历史。当历史超过预算时，用 LLM 将旧对话压缩为摘要，保留关键事实和决策，丢弃冗余的来回确认。目标：用 10% 的 token 保留 90% 的关键信息。

4. 按需检索，不要预加载

不要在对话开始时就把所有可能用到的知识都塞进上下文。让 Agent 根据当前任务动态决定需要检索什么知识。这既节省 token，又减少"Lost in the Middle"的影响。

5. 结构化优于自然语言

上下文中的信息尽量用结构化格式（JSON、XML、Markdown 表格）而非自然语言段落。结构化信息更容易被模型准确提取和引用，尤其在长上下文中。

6. 监控上下文利用率

在生产环境中持续监控每层的 token 使用率、淘汰频率、缓存命中率。这些指标能帮你发现上下文设计的问题——如果历史层频繁淘汰，说明对话太冗长；如果知识层利用率低，说明检索精度不够。
