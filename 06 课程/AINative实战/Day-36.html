📖 今日导读

  • 同时有 3 个 MCP Server 可用，模型怎么选对工具？

🔍 核心概念

1. Agent 编排模式：从 ReAct 到分层架构

在 Day-6 和 Day-21 中，我们重点学了 ReAct 模式——思考、行动、观察的循环。ReAct 适合单目标、步骤较少的任务，但在生产环境中，复杂任务需要更强大的编排模式：

模式一：Plan-and-Execute（规划-执行）

Agent 先制定完整计划，再逐步执行。适合任务步骤可预知的场景。

用户目标 → 生成执行计划 [Step1, Step2, Step3...] 
  → 执行 Step1 → 检查结果
  → 执行 Step2 → 检查结果
  → ... → 汇总交付

与 ReAct 的区别：ReAct 是"走一步看一步"，Plan-and-Execute 是"先画地图再出发"。当任务有 10+ 步骤时，Plan-and-Execute 能避免 Agent 在中间"迷路"。

模式二：Hierarchical Agent（分层 Agent）

一个"主管 Agent"负责拆解任务和分配，多个"工人 Agent"各司其职。这是 2025-2026 年最主流的生产架构：

用户请求
  → Supervisor Agent（理解意图、拆解子任务、分配给工人）
    → Worker A（查询数据库）
    → Worker B（调用外部 API）
    → Worker C（生成报告）
  → Supervisor 汇总结果 → 交付用户

模式三：Graph-based Orchestration（图编排）

用有向图定义 Agent 的工作流，每个节点是一个工具调用或决策点，边代表条件分支。LangGraph 是这一模式的代表框架。适合需要精确控制流程的业务场景（如审批流、多条件分支）。

模式 适用场景 优势 劣势
ReAct 简单问答、单工具调用 实现简单、灵活 步骤多时容易失控
Plan-and-Execute 多步骤任务、项目规划 全局视野、可预测 计划可能不准、需重规划
Hierarchical 复杂业务、多领域协作 分工明确、可扩展 通信开销、一致性难保证
Graph-based 审批流、合规流程 精确控制、可审计 设计成本高、灵活性低

2. MCP 生态实战：从协议到插件网络

MCP（Model Context Protocol）在 Day-6 中作为"AI 的 USB-C"被介绍过。经过一年多的爆发式增长，到 2026 年中，MCP 生态已经形成了完整的产业链：

MCP 架构三层模型：

┌─────────────────────────────────────────┐
│           AI 应用层 (Client)             │
│   Claude Desktop / Cursor / 自研应用      │
├─────────────────────────────────────────┤
│           MCP 协议层 (JSON-RPC)          │
│   Resources / Tools / Prompts / Sampling │
├─────────────────────────────────────────┤
│           工具/数据层 (Server)            │
│   GitHub / Slack / DB / 浏览器 / 文件系统  │
└─────────────────────────────────────────┘

MCP Server 的三种能力： - Tools（工具）：Agent 可以调用的函数（如搜索、创建文件） - Resources（资源）：Agent 可以读取的数据（如数据库记录、文件内容） - Prompts（提示模板）：预定义的 Prompt 模板，供 Agent 或用户选用

2026 年 MCP 生态关键数据： - 官方 MCP Server 数量：200+（覆盖 GitHub、Slack、PostgreSQL、Puppeteer 等主流工具） - 社区 MCP Server：2000+（涵盖各种垂直领域） - 支持 MCP 的客户端：Claude Desktop、Cursor、Windsurf、VS Code、Zed 等 30+ 应用 - MCP 已被纳入 OpenAI Agents SDK 和 Google ADK 的工具接口标准

3. 多 Agent 协调：从孤军奋战到团队协作

当单个 Agent 的能力触顶时，Multi-Agent 系统成为必然选择。2025-2026 年出现了两个重要的协调协议：

Google A2A（Agent-to-Agent Protocol，2025 年 4 月）

A2A 解决的是"不同框架的 Agent 如何互相沟通"的问题。如果说 MCP 是 Agent-to-Tool 的标准，A2A 就是 Agent-to-Agent 的标准。核心概念：

  • Agent Card：每个 Agent 的"名片"，描述它能做什么（类似 API 的 OpenAPI spec）
  • Task：Agent 之间的任务委派单元，包含状态机（submitted → working → completed/failed）
  • Message & Artifact：Agent 间通信的消息和交付物

OpenAI Agents SDK 的 Handoff 机制（2025 年 2 月）

Handoff 是一种更轻量的 Agent 间交接模式——当 Agent A 判断用户的请求更适合 Agent B 处理时，直接"转接"：

# 伪代码示意
triage_agent = Agent(
    name="分诊台",
    instructions="判断用户需求类型，转接给对应专家",
    handoffs=[sales_agent, support_agent, tech_agent]
)

4. 可观测性与安全：Agent 的"黑匣子"和"安全带"

生产级 Agent 最容易被忽视但最重要的两个维度：

可观测性三支柱： - Tracing（追踪）：记录 Agent 每一步的 Thought → Action → Observation，形成完整的执行链路 - Metrics（指标）：工具调用次数、成功率、延迟、Token 消耗、单次任务成本 - Logging（日志）：结构化日志用于回溯和 Debug

安全四层防护： - Input Guardrail（输入护栏）：过滤恶意/越权请求，不让 Agent 处理不该处理的事 - Tool Permission（工具权限）：区分"只读"和"写入"工具，写入操作需人工确认 - Output Guardrail（输出护栏）：检查 Agent 的最终回复是否泄露敏感信息 - Budget Guard（预算守卫）：限制单次任务的最大工具调用次数和 Token 消耗

案例一：Claude Code —— 终端级编程 Agent 的生产实践

Anthropic 于 2025 年 2 月发布的 Claude Code 是一个运行在终端中的编程 Agent。它不是一个 IDE 插件，而是一个独立的 Agent 进程，能够：

  • 读写文件系统、执行 Shell 命令、运行测试
  • 通过 MCP 连接 GitHub、数据库、CI/CD 等外部工具
  • 支持多 Agent 编排（subagent 模式，可 spawn 子 Agent 处理子任务）

关键工程设计决策： 1. Tool Permission 分级：读取文件默认允许，写入/删除需要用户确认，执行命令有沙箱限制 2. 上下文窗口管理：当对话过长时，自动压缩历史，保留关键上下文 3. Human-in-the-Loop：关键操作（如 git push、删除文件）必须人工确认 4. 可观测性：内置 Tracing，每步工具调用都有详细的输入/输出日志

Salesforce 在 2024 年 Dreamforce 大会发布 Agentforce，并在 2025 年推出 2.0 版本。它是一个面向企业的 Multi-Agent 平台，核心特点：

关键数据： Agentforce 2.0 发布后 6 个月内，Salesforce 报告超过 3000 家企业客户部署了 Agent，平均处理效率提升 40%，客户满意度提升 25%。

💻 实战代码

下面是一个生产级 ReAct Agent 框架的完整实现，包含：工具注册与路由、错误处理与重试、执行追踪（Tracing）、预算守卫、以及 MCP 工具集成接口。纯 Python 标准库实现，无需 API Key 即可运行理解架构。

"""
生产级 ReAct Agent 框架
======================
特性：
1. 工具注册与自动路由
2. 错误处理与重试机制
3. 完整执行追踪（Tracing）
4. 预算守卫（调用次数 + Token 限制）
5. MCP Server 接口预留
"""

import json
import time
import uuid
from dataclasses import dataclass, field
from typing import Any, Callable


# ============ 工具注册系统 ============

@dataclass
class ToolDef:
    """工具定义"""
    name: str
    description: str
    parameters: dict  # JSON Schema 格式
    handler: Callable  # 实际执行函数
    is_read_only: bool = True  # 是否只读（写入类工具需确认）
    max_retries: int = 2
    timeout_sec: float = 10.0


class ToolRegistry:
    """工具注册中心 —— 支持动态注册、分类查询"""

    def __init__(self):
        self._tools: dict[str, ToolDef] = {}

    def register(self, tool: ToolDef):
        """注册一个工具"""
        self._tools[tool.name] = tool
        print(f"  [Registry] 已注册工具: {tool.name} ({'只读' if tool.is_read_only else '写入'})")

    def get(self, name: str) -> ToolDef | None:
        return self._tools.get(name)

    def list_tools(self) -> list[dict]:
        """生成工具描述列表（供 LLM 选择工具时使用）"""
        return [
            {
                "name": t.name,
                "description": t.description,
                "parameters": t.parameters,
                "is_read_only": t.is_read_only,
            }
            for t in self._tools.values()
        ]

    def execute(self, name: str, args: dict) -> dict:
        """执行工具调用，含重试和错误处理"""
        tool = self._tools.get(name)
        if not tool:
            return {"success": False, "error": f"工具 '{name}' 未注册"}

        last_error = None
        for attempt in range(1, tool.max_retries + 1):
            try:
                start = time.time()
                result = tool.handler(**args)
                elapsed = time.time() - start
                return {
                    "success": True,
                    "result": result,
                    "elapsed_ms": round(elapsed * 1000, 1),
                    "attempt": attempt,
                }
            except Exception as e:
                last_error = str(e)
                print(f"  [Retry] 工具 {name} 第 {attempt} 次调用失败: {last_error}")
                if attempt < tool.max_retries:
                    time.sleep(0.5 * attempt)  # 指数退避

        return {"success": False, "error": last_error, "attempts": tool.max_retries}


# ============ 执行追踪（Tracing） ============

@dataclass
class TraceStep:
    """单步执行记录"""
    step_id: str
    thought: str
    action: str | None
    action_args: dict | None
    observation: str
    success: bool
    elapsed_ms: float
    token_estimate: int


@dataclass
class ExecutionTrace:
    """完整的 Agent 执行追踪"""
    trace_id: str
    user_query: str
    steps: list[TraceStep] = field(default_factory=list)
    final_answer: str = ""
    total_tokens: int = 0
    total_tool_calls: int = 0
    total_elapsed_ms: float = 0
    budget_exceeded: bool = False

    def add_step(self, step: TraceStep):
        self.steps.append(step)
        self.total_tokens += step.token_estimate
        if step.action:
            self.total_tool_calls += 1

    def summary(self) -> dict:
        return {
            "trace_id": self.trace_id,
            "query": self.user_query[:80],
            "steps": len(self.steps),
            "tool_calls": self.total_tool_calls,
            "total_tokens": self.total_tokens,
            "elapsed_ms": round(self.total_elapsed_ms, 1),
            "budget_exceeded": self.budget_exceeded,
            "success": bool(self.final_answer),
        }


# ============ 预算守卫 ============

@dataclass
class BudgetGuard:
    """预算限制"""
    max_tool_calls: int = 10
    max_tokens: int = 4000
    max_elapsed_sec: float = 60.0

    def check(self, trace: ExecutionTrace) -> str | None:
        """检查是否超预算，返回 None 表示正常，否则返回原因"""
        if trace.total_tool_calls >= self.max_tool_calls:
            return f"工具调用次数已达上限 ({self.max_tool_calls})"
        if trace.total_tokens >= self.max_tokens:
            return f"Token 消耗已达上限 ({self.max_tokens})"
        if trace.total_elapsed_ms / 1000 >= self.max_elapsed_sec:
            return f"执行时间已达上限 ({self.max_elapsed_sec}s)"
        return None


# ============ 模拟 LLM（演示用） ============

class MockLLM:
    """
    模拟 LLM 的工具选择能力。
    在真实系统中，这里调用 OpenAI/Anthropic/本地模型的 API。
    """

    def __init__(self, tools: list[dict]):
        self.tools = tools
        # 模拟推理规则：根据关键词匹配工具
        self._rules = {
            "天气": ("get_weather", lambda q: {"city": "北京"}),
            "计算": ("calculator", lambda q: {"expression": _extract_math(q)}),
            "搜索": ("web_search", lambda q: {"query": q.replace("搜索", "").strip()}),
            "数据库": ("query_db", lambda q: {"sql": "SELECT * FROM orders LIMIT 5"}),
        }

    def think(self, query: str, history: list[dict]) -> dict:
        """模拟 LLM 思考：返回 Thought + Action"""
        # 检查历史是否已有足够信息来回答
        if history and any("result" in str(h.get("observation", "")) for h in history[-2:]):
            return {
                "thought": "已有足够信息，可以给出最终答案。",
                "action": None,
                "final_answer": f"根据查询结果，已为您整理好信息。以下是基于 '{query}' 的分析：{history[-1].get('observation', '')[:200]}"
            }

        # 匹配工具
        for keyword, (tool_name, arg_fn) in self._rules.items():
            if keyword in query:
                return {
                    "thought": f"用户的问题涉及'{keyword}'，需要调用 {tool_name} 工具获取信息。",
                    "action": tool_name,
                    "args": arg_fn(query),
                }

        # 无需工具，直接回答
        return {
            "thought": "这是一个通用问题，无需调用工具，直接回答。",
            "action": None,
            "final_answer": f"关于'{query}'：这是一个很好的问题。在实际系统中，LLM 会基于上下文给出详细回答。当前是模拟环境，建议接入真实 LLM API 以获得完整体验。",
        }


def _extract_math(text: str) -> str:
    """提取文本中的数学表达式"""
    import re
    match = re.search(r'[\d\+\-\*/\(\)\.\s]+', text)
    return match.group().strip() if match else "1+1"


# ============ 生产级 ReAct Agent ============

class ProductionReActAgent:
    """
    生产级 ReAct Agent
    集成：工具注册、执行追踪、预算守卫、错误处理
    """

    def __init__(self, registry: ToolRegistry, budget: BudgetGuard | None = None):
        self.registry = registry
        self.budget = budget or BudgetGuard()
        self.llm = MockLLM(registry.list_tools())

    def run(self, query: str) -> ExecutionTrace:
        """执行一个完整的 Agent 任务"""
        trace = ExecutionTrace(
            trace_id=str(uuid.uuid4())[:8],
            user_query=query,
        )
        start_time = time.time()
        history = []

        print(f"\n{'='*60}")
        print(f"🤖 Agent 开始处理: {query}")
        print(f"   Trace ID: {trace.trace_id}")
        print(f"{'='*60}")

        max_steps = 6  # 防止无限循环
        for step_num in range(1, max_steps + 1):
            # 1. 预算检查
            budget_reason = self.budget.check(trace)
            if budget_reason:
                print(f"\n⚠️  预算超限: {budget_reason}")
                trace.budget_exceeded = True
                trace.final_answer = f"任务因预算限制未能完成：{budget_reason}。已完成 {trace.total_tool_calls} 次工具调用。"
                break

            # 2. LLM 思考
            decision = self.llm.think(query, history)
            thought = decision["thought"]
            print(f"\n--- Step {step_num} ---")
            print(f"💭 Thought: {thought}")

            # 3. 如果 LLM 决定直接回答
            if decision.get("action") is None:
                trace.add_step(TraceStep(
                    step_id=f"{trace.trace_id}-{step_num}",
                    thought=thought,
                    action=None,
                    action_args=None,
                    observation="（无需工具调用）",
                    success=True,
                    elapsed_ms=0,
                    token_estimate=len(thought) // 4,
                ))
                trace.final_answer = decision.get("final_answer", "")
                print(f"✅ Final Answer: {trace.final_answer[:200]}")
                break

            # 4. 执行工具调用
            action = decision["action"]
            args = decision.get("args", {})
            tool_def = self.registry.get(action)

            # 4a. 写入类工具需确认
            if tool_def and not tool_def.is_read_only:
                print(f"🔒 写入操作确认: {action}({args})")
                # 生产环境中此处暂停等待用户确认
                # 这里自动批准用于演示

            print(f"🔧 Action: {action}({json.dumps(args, ensure_ascii=False)})")

            result = self.registry.execute(action, args)
            success = result["success"]
            observation = result.get("result", result.get("error", "未知结果"))
            elapsed = result.get("elapsed_ms", 0)

            print(f"👁️  Observation: {str(observation)[:200]}")
            if not success:
                print(f"❌ 工具调用失败: {result.get('error')}")

            # 5. 记录追踪
            trace.add_step(TraceStep(
                step_id=f"{trace.trace_id}-{step_num}",
                thought=thought,
                action=action,
                action_args=args,
                observation=str(observation),
                success=success,
                elapsed_ms=elapsed,
                token_estimate=(len(thought) + len(str(observation))) // 4,
            ))

            # 6. 更新历史
            history.append({
                "thought": thought,
                "action": action,
                "observation": str(observation),
            })

        # 如果循环结束还没给最终答案
        if not trace.final_answer:
            trace.final_answer = f"经过 {len(trace.steps)} 步推理，已收集到相关信息。在实际系统中，LLM 会整合所有观察结果给出最终回答。"

        trace.total_elapsed_ms = (time.time() - start_time) * 1000

        print(f"\n{'='*60}")
        print(f"📊 执行摘要:")
        summary = trace.summary()
        for k, v in summary.items():
            print(f"   {k}: {v}")
        print(f"{'='*60}\n")

        return trace

def get_weather(city: str = "北京") -> str:
    """模拟天气查询"""
    # 生产环境中调用真实天气 API
    return f"{city}今日天气：多云，气温 25-32°C，湿度 65%，东南风 3 级。建议带伞。"

def calculator(expression: str = "1+1") -> str:
    """安全计算器"""
    allowed_chars = set("0123456789+-*/().% ")
    if not all(c in allowed_chars for c in expression):
        raise ValueError(f"不安全的表达式: {expression}")
    try:
        result = eval(expression)
        return f"{expression} = {result}"
    except Exception as e:
        raise ValueError(f"计算错误: {e}")

def web_search(query: str = "") -> str:
    """模拟搜索"""
    return f"搜索 '{query}' 的结果：找到 3 条相关信息。(1) 相关行业报告显示增长趋势明显 (2) 最新技术方案已更新 (3) 社区讨论热度上升"

def query_db(sql: str = "") -> str:
    """模拟数据库查询"""
    return f"执行 SQL: {sql} → 返回 5 条记录，包含 order_id, customer, amount, status 字段。"

✅ 最佳实践

1. 工具设计：宁少勿多，宁简勿繁

工具数量不是越多越好。Berkeley Function Calling Leaderboard 的数据显示，当可用工具超过 15 个时，主流 LLM 的工具选择准确率会从 92% 下降到 78%。建议每个 Agent 的工具集控制在 8-12 个以内，超出时用分层 Agent 或工具路由来分流。

2. 错误处理：假设每个工具都会失败

生产环境中，工具调用的失败是常态而非异常。必须实现：重试机制（指数退避）、降级策略（主工具失败后用备选工具）、超时控制（避免单个工具卡死整个 Agent）。经验法则：给每个工具设置 2-3 次重试，超时 10-30 秒。

3. 预算守卫：给 Agent 装上"刹车"

没有预算限制的 Agent 是一个定时炸弹。必须设置三重限制：最大工具调用次数（防止无限循环）、最大 Token 消耗（控制成本）、最大执行时间（保证用户体验）。建议为不同用户等级设置不同预算。

4. Human-in-the-Loop：区分"读"和"写"

只读操作（查询、搜索、计算）可以全自动执行。但任何"写入"操作（发送邮件、修改数据库、删除文件）都应该暂停等待人工确认。这是 2025-2026 年所有成功 Agent 产品的共识——Claude Code、Cursor、Agentforce 都遵循这一原则。

5. 可观测性优先：先有 Tracing，再谈优化

在上线 Agent 之前，必须先建好 Tracing 系统。没有 Tracing 的 Agent 就像没有日志的服务器——出了问题你完全不知道发生了什么。建议使用 Langfuse（开源）或 LangSmith 来记录每一步的 Thought、Action、Observation、延迟和成本。

6. MCP Server 管理：治理胜于集成

当接入多个 MCP Server 时，需要建立治理机制：工具命名规范（避免同名冲突）、权限分组（按敏感级别分组）、健康检查（定期检测 MCP Server 是否在线）、版本管理（工具接口变更时的兼容性处理）。

🤔 思考题

  1. 编排模式选择：你的产品中有一个"帮用户做竞品分析"的 Agent 功能，需要同时搜索网页、查询数据库、读取内部文档，最后生成报告。你会选择哪种编排模式（ReAct / Plan-and-Execute / Hierarchical / Graph-based）？为什么？如果任务中途某个工具持续失败，你的降级策略是什么？

  2. MCP vs 原生 API：MCP 提供了统一的工具接入标准，但相比直接调用原生 API，MCP 多了一层协议抽象，会引入额外的延迟和复杂度。在什么场景下你会选择直接用原生 API 而不是 MCP？在什么场景下 MCP 的统一性优势能压过这些成本？
