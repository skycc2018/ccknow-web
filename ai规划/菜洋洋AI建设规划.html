一、总体规划

建设统一的企业级 AI 产品体系。整体形成 "AI 应用触点 + Agent Runtime + AI Capability Gateway + AI 能力基础设施 + 统一观测运营" 的产品架构，并以统一 Identity、权限与审计能力贯穿整个体系。

整体建设目标是： - 一方面能够快速开发、发布和运营各类 Agent，支撑 洋洋 AI、AI 原生业务系统以及"传统业务系统 + AI"等不同形态的应用； - 另一方面将公司的业务系统、数据、Skill、知识、模型等能力以统一方式开放给 Agent，使 Agent 能够在明确的身份和权限边界内自主发现、调用和组合企业能力。

整体建设不是一次性搭建一个"大而全"的 AI 平台，而是先形成 Agent 开发、运行、发布、调用企业能力和统一观测的基本闭环，再伴随业务发展逐步增强数据能力、编排能力和 AI 质量评测能力。 !Pasted image 20260817111951.png

二、用户中心建设

用户中心承担公司 AI 体系统一身份管理和用户识别职责，为所有 AI 产品提供统一的 Identity 基础。

2.1 统一 Identity

建设公司统一 AI Identity 体系，为人员、Agent、应用等对象提供唯一身份标识。

初期重点以公司员工身份为主，在现有用户体系基础上建立统一 AI 身份，并通过 Token 作为各 AI 系统之间统一传递的身份凭证。

后续身份体系逐步扩展至： - Human：员工、业务人员等真实用户； - Agent：具有独立运行身份的 Agent； - Application：业务系统中的 AI 应用； - Service：后台服务及自动化任务。

目标是避免每个 AI 应用独立建立用户、独立鉴权，形成统一的身份来源。

2.2 统一身份认证与 Token

提供统一 Token 签发、校验和透传能力。

所有基于 Agent Runtime 和 AI Capability Gateway 的请求尽量携带统一身份 Token，由能力网关完成身份确认，再将身份信息向下游业务能力透传，使 CRM、WMS、BI 等系统能够识别当前请求对应的具体用户。

这样能够支持"以当前用户身份调用能力"，例如销售 Agent 调用 CRM 时，只返回该销售本人有权限查看的数据。

2.3 用户与 AI 应用关系

用户中心同时维护用户与 Agent、应用之间的可见关系，为 洋洋 AI 门户及 Agent 发布提供统一的用户范围配置能力，例如销售、售后、财务、管理人员等不同角色看到不同 Agent。

三、AI 触点建设

AI 触点主要形成三种产品形态，不要求所有 AI 能力都以聊天机器人形式呈现，而是根据业务场景选择合适的产品形态。

3.1 洋洋 AI：统一 AI 体验门户

洋洋 AI 作为公司内部主要的 AaaS（Agent as a Service）服务入口，承担公司各类通用 Agent 和 AI 服务的统一承载和使用。

核心建设包括： - 统一 Agent / AI 服务注册和上架； - 支持 Agent Runtime 开发的 Agent 一键发布； - 支持配置 Agent 可见范围及使用角色； - 支持会话历史、会话切换和会话分享； - 支持统一的用户身份和权限控制； - 支持标准 OpenAI 协议接入外部 Agent 或 AI 能力； - 后续逐步建设 Agent 分类、搜索、推荐等能力。

洋洋 AI 的定位不是单纯的 Chat Portal，而是公司内部各种 AI 能力的统一消费入口。

3.2 AI 原生业务系统

针对本身需要较强业务流程、数据管理和运营能力的场景，建设独立 AI 原生业务系统。

这类产品以 Agent 为核心，但不局限于聊天界面，而是结合业务数据、工作流和传统业务功能共同形成完整产品。

例如工厂菜品研发知识沉淀项目，可以由 Agent 负责知识分析、沉淀和交互，同时结合产品研发管理、PM 助理、知识归档和竞争力看板等功能形成完整系统。

后续部分业务需求可视场景采用 AI 原生方式设计，而非在原有系统外面增加一个聊天窗口。

3.3 业务系统 + AI

对于已有成熟业务系统，不进行大规模重构，而是通过 Agent、AI 服务或智能能力嵌入已有系统。

典型场景包括： - CRM 商机旅程总结； - 销售录音分析； - AI 录音质检； - 客诉识别与自动登记； - 工单总结； - 业务数据智能分析等。

此类场景重点依托 Agent Runtime 和 AI Capability Gateway 快速建设，减少重复开发 AI 基础能力。

四、Agent Runtime 建设

构建统一的 Agent Runtime，提供统一"开发脚手架"，帮助实现 Agent 规范开发、运行和管理。

Agent Runtime 是整个 AI 产品体系的核心基础设施，所有 AI 应用尽量统一基于 Runtime 运行。

4.1 Runtime 核心能力

封装 Agent 通用运行能力，减少不同 AI 应用重复实现。

主要包括： - 统一用户认证与身份获取； - Session、会话历史和上下文管理； - Model Provider 配置和动态切换； - Skill、Tool、MCP 等能力加载； - Agent Persona / Prompt 配置； - Agent 配置远程管理； - 运行日志； - Token 与调用量统计； - 异常信息采集； - Agent 版本管理； - 发布、灰度和回滚； - 运行状态管理。

4.2 Harness 解耦

Agent Runtime 不绑定具体 Agent Harness。

内部通过统一 Runtime Contract 与开源成熟 Agent Harness 对接，目前可以优先适配现有成熟方案，后续根据市场技术发展替换不同 Harness。

目标是避免平台核心能力绑定某一个具体 Agent 框架，保证未来能够持续吸收 OpenClaw、Claude Code、其他 Agent Runtime 等新一代方案的能力。

4.3 Agent 开发与管理

建设统一 Agent Console，为开发人员和业务人员提供可视化 Agent 开发能力。

支持： - Agent 创建； - 人设配置； - Skill 配置； - Tool / MCP 配置； - Knowledge / Data 配置； - Model 配置； - 调试运行； - 版本管理； - 发布与回滚； - 异常分析； - 基础运营数据查看。

其中逐步开放业务人员自主创建 Agent 的能力，使业务人员能够基于公司已有 Skill、MCP、知识和数据能力自行组合 AI 服务，而无需每一个 AI 场景都依赖研发团队完整开发。

4.4 两种运行形态

Agent Runtime 同时支持服务端和客户端两种运行模式。

服务端 Runtime：支撑企业内部各种 AaaS Agent 和业务系统中的 AI 能力。

客户端 Runtime：将 Agent Runtime 打包为个人电脑上的 AI Agent，允许 Agent 使用本地文件、本地工作数据和个人工具，同时通过 AI Capability Gateway 调用公司业务系统能力，逐步形成个人 AI 助手。

后续随着业务发展，再增加编排型 Agent、Workflow Agent、多 Agent 协同等能力，以满足对流程确定性要求更高的严肃业务场景。

五、AI Capability Gateway 建设

AI Capability Gateway 是 Agent 与企业能力之间的统一连接层。

其核心目标不是简单做 API Gateway，而是建立统一的 AI Capability 抽象、发现、授权和调用机制。

在上层统一将 MCP、Skill、Knowledge、Data、Model 等抽象为可被 Agent 使用的 Capability，底层保持各自不同的实现方式。

5.1 Capability Registry

建立企业 AI Capability 注册与目录能力。

每项能力统一记录： - 能力名称； - 能力描述； - 能力类型； - 调用方式； - 入参和返回结构； - 所属系统； - 所属部门； - 权限要求； - 使用范围； - 版本； - Owner。

Agent Runtime 可通过标准接口获取当前身份能够使用的能力列表及调用指南，实现动态 Capability Discovery。

5.2 Capability Access Control

统一控制用户、Agent 对公司能力的访问权限。

权限控制不仅控制"能不能调用"，还需要逐步细化到"能查看什么数据、能执行什么操作"。

能力网关负责完成身份识别、权限判断，并将用户身份透传至下游能力。

5.3 MCP 平台

MCP 平台负责统一接入和管理企业业务系统提供的原子能力。

重点接入： - CRM； - WMS； - SRM； - 洋洋懂菜； - BI； - ERP； - 工单及售后系统； - 其他内部业务系统。

MCP 平台重点建设连接器管理、工具注册、Schema 管理、权限映射、版本管理和运行监控。

对于已有业务系统能力，优先通过 MCP 标准方式向 Agent 开放，避免每个 Agent 重复对接业务系统。

5.4 Skill 商店

Skill 商店负责公司内部 Skill 的集中管理和复用。

Skill 重点解决"Agent 怎么做事"的问题，而 MCP 更侧重"Agent 能调用什么"。

主要建设： - Skill 注册； - Skill 发布； - Skill 版本管理； - Skill 更新； - Skill Owner； - 使用范围； - Agent 引用关系； - Skill 审核； - Skill 推送和分发； - 强制升级； - 使用情况统计。

允许个人或 Agent 开发团队向 Skill 商店提交 Skill，并通过统一机制完成审核、发布和分发，避免优秀能力沉淀在单个项目中无法复用。

5.5 Agent Data / 文件数据中心

现阶段不将所有企业数据都强制转化为 RAG。

针对全量商品数据、原始经营数据、服务日志、用户搜索历史、浏览历史等大文件、离散原始数据，建设面向 Agent 的文件数据能力。

核心能力包括： - 数据集注册； - 文件上传及管理； - 数据集版本； - 数据权限； - 数据下载； - Agent 访问授权； - 数据生命周期管理。

Agent 获得权限后，可以直接下载原始数据，并通过代码、Python、SQL 等方式自行分析。

该能力用于弥补传统 RAG 在大规模结构化数据、完整原始数据处理场景中的不足。

5.6 知识库平台

知识库继续承担企业文档、制度、产品资料等非结构化知识的管理与 RAG 服务。

重点建设： - 知识采集； - 文档解析； - 分段与索引； - 向量检索； - Rerank； - 权限过滤； - Knowledge API； - Agent 接入。

知识库和 Agent Data Hub 分工明确： - 知识库：解决"Agent 从知识中检索答案"； - Data Hub：解决"Agent 获取完整原始数据后自行分析"。

5.7 Model Gateway

统一管理公司内部各种模型和模型 API，不要求业务 Agent 自己保存大模型 API Key。

主要建设： - 模型统一接入； - API Key 管理； - 模型路由； - 调用限流； - Token 配额； - 成本统计； - 超限控制； - 故障切换； - Provider Fallback； - 不同 Agent / 部门的模型策略。

后续随着模型种类增加，逐步接入文本、Embedding、Rerank、OCR、ASR、视觉等模型服务。

5.8 Text2SQL

根据业务发展逐步建设企业级 Text2SQL 能力，用于自然语言查询结构化数据。

该能力不作为第一阶段重点，需要优先解决： - 数据表和字段权限； - 数据脱敏； - SQL 生成安全； - SQL 执行范围； - 查询结果限制； - 审计。

避免因为模型自动生成 SQL 导致越权查询。

5.9 MaaS

MaaS 暂作为后续规划。

目前公司内部如果缺少成熟私有化小模型能力，OCR、ASR 等模型服务优先通过 MCP 或标准服务方式提供给 Agent，不急于建设完整 MaaS 平台。

随着企业内部模型数量增加、私有化模型部署需求提高后，再逐步建设统一模型训练、部署、推理和版本管理能力。

5.10 本体

本体目前实际商业落地中效果并不好，前期依赖大量人力整合业务规则，且面对灵活的业务场景严重依赖后期维护。存在高投入低回报的问题，因此滞后规划，保持关注，待有明确的建设方法论后推进。

六、一站式 AI 观测与运营平台建设

建立公司统一 AI 观测运营平台，解决 AI 应用快速增长后，各项目分别建设后台、日志、Token 统计和运行监控导致的信息割裂问题。

第一阶段重点建设 Trace + 运行观测 + 统一运营，Eval 暂不作为核心建设内容，待 Agent 数量和业务成熟度提升后再逐步引入。

6.1 统一 Trace

Trace 是平台重点能力。

传统业务系统通常关注一条请求是否成功，而 Agent 一次任务可能包含多轮模型调用、Skill 调用、MCP 调用、知识检索和代码执行。

平台需要形成完整的 Agent 执行链路，支持从一次完整任务向下追踪每一步执行过程。

重点记录： - Trace； - Span； - LLM 调用； - Tool / MCP 调用； - Skill； - Knowledge Retrieval； - Token； - Latency； - Error； - Model； - Agent Version； - 用户身份。

最终可以回答：

谁在什么时间，以哪个 Agent 身份，调用了什么能力，经过了哪些步骤，使用了什么模型，产生了什么结果。

6.2 运行状态与运营数据

统一查看所有 AI 服务： - 在线实例； - Agent 数量； - 调用次数； - 活跃用户； - Token 消耗； - 模型消耗； - 成本； - 错误率； - 响应时间； - 高频异常； - 会话量。

同时支持 Agent Owner 对自己的 Agent 查看运行和运营数据。

6.3 统一日志接入

支持两种接入方式：

第一种：由 Agent Runtime 提供 SDK，所有基于 Runtime 的 Agent 默认接入平台。

第二种：对第三方 Agent 开放标准 API，使外部 Agent 服务能够主动上报： - 日志； - Trace； - Token； - 调用结果； - 服务状态。

这样即使不是菜洋洋 Runtime 开发的 Agent，也可以纳入统一观测体系。

6.4 远程运维

对于由 Agent Runtime 管理的服务，逐步支持： - 实例状态查看； - 配置读取； - 参数修改； - 模型切换； - Skill 更新； - 重启； - 版本切换； - 回滚。

形成从开发、发布到运行和运维的统一闭环。

七、AI 身份、权限与审计体系

不单独建设一个"AI Governance 平台"，而是将身份、权限和审计能力落到用户中心、AI Capability Gateway、Agent Runtime 和观测运营平台中，形成横向的统一体系。

7.1 身份

统一管理 Human、Agent、Application、Service 等 AI 体系参与者的身份。

核心要求是所有 AI 请求均能够明确识别：谁发起、哪个 Agent 执行、哪个应用承载。

7.2 权限

权限围绕"用户 → Agent → Capability → Data"建立统一控制链路。

权限控制逐步从简单的 Agent 可见性，扩展到能力权限、操作权限、数据范围权限。

7.3 审计

所有关键 AI 行为进入统一 Trace / Audit 体系，包括： - Agent 创建； - Agent 发布； - Agent 调用； - Capability 调用； - 数据访问； - 模型调用； - Skill 更新； - 权限变更； - 外部 Agent 接入。

通过统一审计记录，支持后续问题追踪、安全检查和责任定位。

整体上，这套体系不额外形成一个独立产品，而是作为 AI 平台的基础能力贯穿现有核心系统。

八、后续演进方向

当前阶段优先建立 Agent 体系最核心的基础设施，重点解决"能开发、能运行、能接入企业能力、能统一管理、能看清运行过程"。

后续随着 AI 应用规模和业务复杂度提升，再逐步增加： - 第一阶段重点： - 用户中心 - 洋洋 AI - Agent Runtime - AI Capability Gateway - 观测运营平台 - 统一身份、权限、审计 - 后续逐步演进： - 数据能力增强 - 编排能力增强 - AI 质量评测（Eval）能力

其中 Eval 暂作为后续演进能力，当前不单独做重型评测平台，优先把 Trace 和完整运行数据积累起来，为后续自动化评测提供基础。

最终形成一套以 Agent 为核心、以企业能力开放为基础、以统一 Identity 和权限审计为保障、以 Trace 为运行基础设施的菜洋洋企业 AI 产品体系。
