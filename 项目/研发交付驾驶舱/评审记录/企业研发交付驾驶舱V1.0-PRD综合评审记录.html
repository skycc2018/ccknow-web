企业研发交付驾驶舱 V1.0 — PRD 综合评审记录

评审对象： 企业研发交付驾驶舱V1.0-PRD骨架（V0.6）+ 线框图索引（V1.3，共 43 页面）

合并来源： Claudian 评审建议 + FDE（全栈开发工程师）差异清单 + 评审会记录

评审日期： 2026-07-18

评审结论： 有条件通过，需修正 4 项严重问题后方可进入开发

问题统计

优先级 数量 处理要求
🔴 严重（逻辑矛盾 / 流程断裂） 4 必须修正，否则开发无法启动
🟠 缺陷（功能不完整 / 交互不清） 6 建议修正，影响功能完整性

📋 待确认事项 17 评审会逐项拍板

一、评审总览与结论

1.1 总体评价

系统按"角色优先"设计，定位清晰，覆盖了业务用户、产品经理、研发团队、CIO 四类角色的核心诉求。PRD 骨架整体结构清晰，角色化设计理念合理，数据模型基本完整。风险中心和数据分析驾驶舱是价值亮点，可支撑 CIO 提前介入交付风险。

1.2 主要风险点

风险等级 问题类别 说明
🔴 高 需求状态机不一致 PRD 与线框图出现 3 种以上状态流，直接影响开发实现
🔴 高 Version / Release 概念混淆 产品版本与技术发布混用，导致状态联动和统计口径混乱
🟡 中 ProductSchedule实体缺失 仅在 ER 图和数据流中出现，缺少字段字典和表设计输入
🟡 中 风险规则触发条件模糊 "工期""测试""变更"等口径未定义，影响规则引擎实现
🟡 中 人力负载计算口径不清 时间窗口、任务状态范围、PM 负载来源未明确
🟡 中 数据权限规则缺位 全部 / 本部门 / 本项目 / 仅自己未细化到页面
🟢 低 界面颜色与状态术语不一致 需统一 Design Token，但不阻塞开发

1.3 范围建议

当前 V1.0 规划 43 个页面、17 个核心实体、7 条风险规则、大屏 + 驾驶舱 + 第三方对接，按 8 周排期压力较大。建议先确定 MVP 核心闭环：

业务提需求 → 产品评审 → 产品排期 → 研发建任务 → 完成任务 → 版本发布 → 需求上线

在该主线跑通之前，大屏、复杂统计、第三方 API 开放等能力建议降级到后续迭代。

1.4 评审结论

PRD 骨架整体结构清晰，角色化设计理念合理，数据模型基本完整。但存在 4 项严重问题需要修正后方可进入开发：

  1. 需求状态枚举必须统一（P1-01）——这是所有功能的基础
  2. 状态流转规则必须明确（P1-02）——否则开发无法实现
  3. "已交付"与"已上线"边界必须清晰（P1-03）——否则业务用户会困惑
  4. 看板列名与状态枚举必须匹配（P1-04）——否则研发看板无法工作

建议产品总监在 1 个工作日内 完成第一轮修复（P1-01~P1-04），修复后组织第二次评审确认，然后进入开发阶段。

二、🔴 严重问题（必须修正）

P1-01 需求状态枚举不一致

来源标记： Claudian P1-01 / FDE §2.1 / 会议#1

问题描述： PRD 中存在多套不同的需求状态定义，互相矛盾。

位置 状态枚举
§5.1.1 我的需求（列表字段） 需求提出 / 产品评审 / 产品排期 / 研发排期 / 开发 / 测试 / 上线
§6.3 Requirement 实体（status） 需求提出 / 产品评审 / 产品排期 / 研发排期 / 开发中 / 已交付 / 已上线 / 已驳回
§5.1.2 生命周期时间轴 7 步线性流程，无"已驳回"分支
业务用户线框图 需求提出 / 产品排期 / 开发中 / 测试中 / 已上线
版本管理 §5.2.5 版本状态：计划中 / 开发中 / 测试中 / 已发布 / 已回滚

矛盾点： - §5.1.1 有「测试」状态，§6.3 没有；§6.3 有「已交付」状态，§5.1.1 没有 - §5.1.1 用「上线」，§6.3 用「已上线」，命名不统一 - §5.1.2 的 7 步线性流程无法表达"已驳回"分支 - 需求状态枚举中没有「测试中」，但任务状态有「待开发 / 开发中 / 联调 / 测试 / 待验收 / 已完成」，业务用户详情页生命周期时间轴却包含「测试」阶段

影响范围： 全系统。所有涉及需求状态展示、筛选、流转的功能都会受影响。

修复建议： 1. 以 §6.3 实体定义为准，统一为 8 个状态：需求提出 / 产品评审 / 产品排期 / 研发排期 / 开发中 / 已交付 / 已上线 / 已驳回 2. §5.1.1 列表字段的状态枚举同步修正 3. §5.1.2 生命周期补充"已驳回"分支（驳回后回到"需求提出"） 4. 线框图中所有涉及状态展示的地方同步更新 5. 需求层不保留「测试」独立状态——测试阶段通过任务状态（待开发→开发中→联调→测试→待验收→已完成）和版本状态（测试中→已发布）体现

验收标准： PRD 全文搜索"状态"相关描述，确保所有位置使用同一套枚举值。

P1-02 需求生命周期与自动流转规则冲突

来源标记： Claudian P1-02 / FDE §4.1 / 会议#6

问题描述： §5.1.2 定义了 7 步线性生命周期，但 §5.2.1 和 §6.4.4 的自动流转规则跳过了中间状态。

线性流程：

需求提出 → 产品评审 → 产品排期 → 研发排期 → 开发 → 测试 → 上线

自动流转规则： - 需求关联开发任务 → 状态自动变为"开发中"（跳过"研发排期"） - 所有任务完成 → 状态自动变为"已交付"（跳过"测试"和"上线"）

FDE 补充歧义： 1. 是在任务创建时立即变更，还是任务从"待开发"变为"开发中"时变更？ 2. 任务回退（从已完成→开发中）时，需求状态是否回退？ 3. 子需求如何参与父需求状态计算？ 4. 测试类型任务是否也算"开发任务"？

影响范围： 需求状态流转的核心逻辑。

修复建议： 1. 明确"研发排期"阶段的触发条件和完成条件： - 触发：技术方案完成（含架构评审通过，如需要） - 完成：任务拆分完毕，所有任务已关联 Sprint 2. 明确"测试"阶段的归属——需求层不保留独立测试状态（与 P1-01 一致） 3. 补充完整的状态流转规则表：

当前状态 触发事件 下一状态 说明
需求提出 产品经理点击"认领" 产品评审 —
产品评审 评审通过 产品排期 —
产品评审 评审拒绝 已驳回 需填写拒绝原因
已驳回 提出人修改并重新提交 需求提出 —
产品排期 排期完成 研发排期 —
研发排期 技术方案完成 + 任务拆分完成 开发中 自动流转
开发中 所有任务已完成 已交付 自动流转
已交付 版本发布 已上线 批量更新

自动流转补充规则：

触发事件 联动行为 备注
需求下第一个任务进入"开发中" 需求 → 开发中 非任务创建即触发
需求下所有非测试任务进入"已完成" 需求 → 已交付 测试任务可单独完成或不阻塞
任意任务从"已完成"回退 需求状态回退到"开发中" 避免状态与实际脱节
版本发布成功 版本内已交付需求 → 已上线 批量更新
项目归档 项目下所有未关闭需求冻结 只读

验收标准： 状态流转表覆盖所有枚举值的入口和出口，无孤立状态。

P1-03 "已交付"与"已上线"的边界模糊

来源标记： Claudian P1-03 / FDE §2.2

问题描述： 需求"已交付"（研发完成）和"已上线"（版本发布）之间存在状态真空。

场景还原： 1. 需求下所有任务完成 → 状态变为"已交付" 2. 但该需求尚未纳入任何版本发布 3. 此时业务用户在 §5.1.1 看到的状态是什么？——PRD 没有定义 4. 版本关联弹窗过滤"已交付"需求（§5.2.5）——需求不在任何版本里 5. 需求处于"已交付"但不是"已上线"——需求"消失"了

影响范围： 业务用户体验。需求交付后到上线前，业务用户看不到需求进展。

修复建议： 1. 明确"已交付"对业务用户的映射：

研发内部状态 业务用户可见状态 说明
需求提出 需求提出 —
产品评审 产品评审 —
产品排期 产品排期 —
研发排期 研发排期 —
开发中 开发中 —
已交付 待上线 对业务用户透明化
已上线 已上线 —
已驳回 已驳回 —
  1. 版本关联弹窗应显示"已交付但未上线"的需求（可选关联）
  2. 补充业务用户视角的状态映射规则

验收标准： 业务用户在任何状态下都能找到自己的需求，无"消失"场景。

P1-04 研发看板列名与任务状态枚举不匹配

来源标记： Claudian P1-04

问题描述： §5.3.6 定义看板列为：待开发 / 开发中 / 联调 / 测试 / 待发布 / 已完成。但 §5.3.2 的任务状态枚举是：待开发 / 开发中 / 联调 / 测试 / 待验收 / 已完成。

矛盾： - 看板有"待发布"列，状态枚举里没有"待发布" - 状态枚举有"待验收"，看板里没有"待验收"列 - 线框图 §04 看板使用的是"待发布"，与 §5.3.2 不一致

影响范围： 研发看板的拖拽交互、任务状态流转。

修复建议： - 方案 A（推荐）：统一为"待验收"，看板列改为：待开发 / 开发中 / 联调 / 测试 / 待验收 / 已完成 - 方案 B：在状态枚举中增加"待发布"，明确"待验收→待发布→已完成"的流转

验收标准： 看板列名与任务状态枚举一一对应。

三、🟠 缺陷问题（建议修正）

P2-01 业务用户提交需求数量限制缺乏弹性

来源标记： Claudian P2-01

位置： §5.1.5 业务规则
