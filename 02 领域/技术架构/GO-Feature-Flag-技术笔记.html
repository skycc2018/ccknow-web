GO Feature Flag 技术笔记

一句话概述

GO Feature Flag 是一个基于 OpenFeature 标准的轻量级自托管功能开关系统，用 Go 编写，MIT 开源。核心卖点是配置即代码（YAML/JSON/TOML 定义开关）+ 多语言 SDK + 渐进式发布 + 10+ 数据导出器，适合需要自托管、轻量级、标准化功能开关的团队。

1. 核心架构

1.1 系统架构总览

1.2 OpenFeature 集成方式

GO Feature Flag 是 OpenFeature 原生实现，不是后来适配的。集成方式有两种：

方式 适用场景 原理
Go 原生 Provider Go 微服务直接集成 直接调用内部评估引擎
OFREP 协议 Java/Python/JS/.NET/Kotlin/PHP/Swift 通过 HTTP 调用 Relay Proxy 的 OFREP 端点 
// Go 原生集成示例
import (
    gofeatureflag "github.com/thomaspoignant/go-feature-flag"
    "github.com/thomaspoignant/go-feature-flag/retriever/filesystemretriever"
)

provider, _ := gofeatureflag.NewProvider(
    gofeatureflag.ProviderOptions{
        Retriever: &filesystemretriever.Retriever{Path: "flags.yaml"},
    },
)
openfeature.SetProvider(provider)
client := openfeature.NewClient("my-app")

// 使用
enabled, _ := client.BooleanValue(
    context.Background(),
    "new-checkout-flow",
    false,  // 默认值
    openfeature.EvaluationContext{
        "targetingKey": user.ID,
        "email":        user.Email,
        "country":      user.Country,
    },
)

关键源码：flagd/resolver.go — OFREP 协议的解析器实现（273行），负责将 HTTP 请求转换为内部评估逻辑。

1.3 Targeting Rules 语法

Flag 支持基于用户属性的定向规则：

my-flag:
  percentage: 100
  true: enabled-variant
  false: disabled-variant
  default: default-variant
  rule: "user.email eq \"beta@test.com\""
  trackEvents: true
  disable: false

支持的运算符： - 比较：eq, ne, gt, lt, gte, lte - 集合：in, not_in - 字符串：regex, contains, starts_with, ends_with - 百分比：percentage（基于用户 ID 哈希的一致性分流）

5. 在 WMS 中的适用性分析

5.1 当前 WMS 的灰度发布需求

根据 ccknow 中的研发体系建设方案，当前发布流程已定义：

功能开关（Feature Flag）控制 → 灰度发布：5% → 20% → 50% → 100% → 全量发布

WMS（仓储物流模块）的特殊需求： - 4 种履约模式的逐步上线：平台仓配 → 租户自履约 → 供应商直发 → 三方物流 - 多租户：不同商户/租户可能使用不同的功能版本 - 库存承诺逻辑变更需要灰度：下单锁定 → 支付扣减 → ERP 回写的三级库存链路 - 履约路由引擎的 A/B 测试：不同路由策略的效果对比

5.3 灰度发布策略与 GO Feature Flag 的结合

WMS 灰度发布流程：

1. 开发完成 → 功能开关默认关闭
   Flag: wms-fulfillment-routing-v2 → percentage: 0

2. 内部测试 → 仅内部用户
   Flag: wms-fulfillment-routing-v2 → rule: "user.email contains \"@company.com\""

3. 小流量灰度 → 5%
   Flag: wms-fulfillment-routing-v2 → percentage: 5, trackEvents: true

4. 扩大灰度 → 20%
   Flag: wms-fulfillment-routing-v2 → percentage: 20

5. 半量 → 50%
   Flag: wms-fulfillment-routing-v2 → percentage: 50

6. 全量 → 100%
   Flag: wms-fulfillment-routing-v2 → percentage: 100

7. 移除开关 → 代码清理
   删除 Flag，代码中移除条件分支

关键优势：通过 trackEvents: true + 数据导出器（BigQuery/Kafka），可以对比新旧路由策略的履约时效、成本、异常率，实现数据驱动的渐进式发布。

6. 局限性与注意事项

6.1 已知限制

  1. 社区规模较小：2k Stars vs Unleash 12k+，遇到问题可能需要看源码
  2. UI Dashboard 功能基础：相比 LaunchDarkly/Unleash 的 UI，GO Feature Flag 的管理界面较简单
  3. 无内置用户管理：Flag 管理权限需要自行实现
  4. 评估规则表达式有限：复杂业务规则可能需要在应用层补充逻辑
  5. WASM 生态仍在演进：Python Provider 基于 WASM，性能和调试工具有待完善

6.2 常见坑

问题 原因 解决方案
Flag 变更不生效 缓存刷新间隔未配置 设置合理的 pollingInterval
百分比分流不一致 用户 ID 哈希变化 确保 targetingKey 稳定
多环境配置混乱 Flag Set 未隔离 使用 Flag Set 按环境/租户隔离
导出数据丢失 导出器配置错误 配置批量大小和导出频率
